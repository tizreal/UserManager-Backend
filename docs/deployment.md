# Security release: deployment runbook

Runbook for deploying the release that introduced role-based authorization, session
revocation, hashed single-use reset tokens and Flyway migrations (V1 baseline, V2–V4). The condensed, ordered checklist with every approval
checkpoint is `docs/deployment-checklist.md`; this runbook explains each step.

**Ground rules**

- Every step marked **[approval]** changes something outside the repository and needs explicit
  approval first.
- **The old Render service is never resumed and no commit older than the release merge is
  ever deployed.** Render does not document whether *Resume* restarts the last built image; on
  the old service that image predates this release and does not support maintenance mode. The release goes to a **new Render
  service** created in maintenance mode. The old service stays suspended until it is deleted.
- The backend stays closed to the public (maintenance mode) until it has been verified.

Versions: Spring Boot 3.4.1, Hibernate 6.6.4, Flyway 10.20.1, PostgreSQL JDBC 42.7.4.

## 1. Preflight (read-only) — done 2026-10-23

`docs/preflight.sql` checks that production matches the V1 baseline (S1–S8), that the data
won't break V2–V4 or the new code (D1–D4), informational context (I1–I3, never proof) and roles
(B1–B6). Two roles may be the same or different: the **migration role** (what Flyway connects
as: `SPRING_FLYWAY_USER` if set, otherwise `DATABASE_USERNAME`) and the **application role**
(`DATABASE_USERNAME`). Run B1–B3 as the migration role and B1 + B5 as the application role;
B6 only if the roles differ. Output rows are labelled **BLOCKER**, **REVIEW** or **OK/INFO**.

| Section | What it verifies | Blocks deployment when |
|---|---|---|
| S1 | `users`, `posts`, `comments` present; `flyway_schema_history`, `password_reset_tokens` absent | A table is missing or already exists |
| S2 | Every mapped column: present, same type; nullability compared | A column is missing or its type differs |
| S3 | Unmapped extra columns | One is NOT NULL without a default |
| S4 | Primary keys `users(user_id)`, `posts(id)`, `comments(id)` | Missing or different |
| S5 | Ids generated by the database | Not generated |
| S6 | Foreign keys posts→users, comments→posts, comments→users | REVIEW only; see D1 |
| S7 | Names V2–V4 create are unused | Any already in use |
| S8 | PostgreSQL ≥ 11; row counts | Older than 11 |
| D1 | No orphaned posts/comments | Any orphan |
| D2 | No case-insensitive duplicate usernames/emails | Any (V2's unique indexes would fail) |
| D3 | No `deleted-user-` usernames | REVIEW: rename first |
| D4 | NULL `email_verified`/username/email/password | REVIEW: those accounts can't sign in |
| I1 | Timestamp anomalies (lower id, later `created_at`) | Never: context only, **not proof** |
| I2 | Id range summary | Never: gaps are **not evidence** of deletion |
| I3 | Demo account state | Never |
| B1–B3 | Migration role can alter `users` and create in `public` | It can't |
| B4 | `DATABASE_URL` host has no `-pooler` (manual) | Pooled with no direct `SPRING_FLYWAY_URL` |
| B5 | Application role has DML on the three tables | It lacks DML |
| B6 | Only if roles differ: default privileges | No default grant: plan explicit grants |

**Production result (2026-10-23):** every S and D check passed; I1 no anomalies; I2 5 users
(ids 1–5), 0 posts, 0 comments; demo account present and verified. B1/B2: `neondb_owner`
owns all three tables; B3 true/true; B5 all OK; B6 not applicable (same role). Render:
`DATABASE_USERNAME=neondb_owner`, no `SPRING_FLYWAY_USER`, `DATABASE_URL` on the direct
endpoint. Consequences: no `SPRING_FLYWAY_*` variables and no grants are needed.

## 2. The migrations and how they can fail

| Migration | Statements | Lock on `users` | Reversibility |
|---|---|---|---|
| V2 | add `role` (default `USER`), CHECK `ck_users_role`, add `token_version` (default 0), unique indexes on `lower(user_name)` and `lower(email)` | ACCESS EXCLUSIVE (column/constraint), SHARE (index build); milliseconds at 5 rows | Additive |
| V3 | create `password_reset_tokens` (+ unique hash, FK to `users` with ON DELETE CASCADE, index) | Brief SHARE ROW EXCLUSIVE for the FK | Additive |
| V4 | add `status` (default `ACTIVE`) + CHECK `ck_users_status`, `deleted_at`, `pending_email` | ACCESS EXCLUSIVE; milliseconds | Additive |

**Transactional behaviour (verified by reading the scripts).** Every statement in V2–V4 is
transactional DDL in PostgreSQL: no `CREATE INDEX CONCURRENTLY`, no `ALTER TYPE ... ADD VALUE`,
no `VACUUM`, no data backfill. Flyway runs **each migration in its own transaction**, so:

- A failing migration is rolled back **completely**, and on PostgreSQL Flyway records **no**
  history row for it (the history insert is in the same transaction). No `flyway repair` is
  needed, and the failed script may be corrected before it is retried.
- Migrations are **not** grouped: an earlier migration that succeeded stays committed. The
  database can therefore end at V1 (baseline only), V2 or V3. The baseline row itself is
  committed before V2 runs.
- In every partial state the application **does not start**: Flyway stops startup, and even
  without that Hibernate validation would fail on the missing columns. The service stays
  closed rather than running against a half-migrated schema.
- `ADD CONSTRAINT` has no `IF NOT EXISTS`, so V2/V4 are not blindly re-runnable if someone
  created those objects by hand. Preflight S7 confirmed none exist; never create them manually.

**Failure scenarios and handling**

| Scenario | What the database looks like | Handling |
|---|---|---|
| A statement fails (e.g. duplicates appear before V2's index) | Last successful version; failed migration absent from history | Service stays down. Diagnose from the log, fix the data **[approval]** or the script (fix-forward PR, CI green), redeploy the same service. Flyway resumes at the first missing version. No restore needed |
| Lock wait: another session holds a lock on `users` (e.g. an idle-in-transaction SQL editor tab) | No lock timeout is configured, so the migration waits; startup hangs until Render's deploy timeout kills it, which closes the connection and rolls back the open migration | Before deploying, run the session check in section 6 and close other sessions. If it happens: identify the blocker with the same query, end it **[approval]**, redeploy |
| Connection lost mid-migration (Neon compute restart, network) | PostgreSQL rolls back the open migration; Flyway's advisory lock is released with the session | Redeploy; Flyway continues from the last committed version |
| A migration was applied but the app misbehaves | Schema at V4, app running | Maintenance mode; fix forward (section 9). The schema changes are additive and are not rolled back |
| Data damaged (not expected from these scripts) | — | Restore (section 5) **[approval]** |

Rehearsed end to end (section 4). `MigrationIT` additionally proves on PostgreSQL 16: baseline
+ V2–V4 on a populated V1 database with exact history; a second run is a no-op; a failing V2
leaves no partial change and no history row (only the committed BASELINE), and after the data
is fixed the next run applies V2–V4 with no repair; a failing V3 leaves the database at V2
(V2 kept, V3 and V4 absent), and the next run applies V3 and V4.

| `RESEND_API_KEY`, `RESEND_FROM_EMAIL` | Copy (email is sent through the Resend API) |

| `DDL_AUTO` | **Do not set** (no longer read) |

**Vercel:** `VITE_API_URL=https://<new-render-host>` (no `/api`, no trailing slash; the app
appends `/api`). Build-time variable: it takes effect on the next build. **Neon:** no change.

**The new backend hostname must be reflected in exactly two places, both in the frontend:**
`VITE_API_URL` (Vercel) and `connect-src` in `vercel.json` (CSP). The backend needs no change:
CORS is keyed on the *frontend* origin, which does not change, and `CLIENT_URL` is the
frontend URL. Verification commands are in section 10.

**Demo seeding:** with `APP_SEED_DEMO=true` every boot upserts `demo`, `ada`, `alan` and
`grace`: profile fields reset, passwords reset (`demo` to the public demo password, the others
to random values), role forced to `USER`, email verified. Never promote any of these four to
admin (the seeder would demote them, and `demo`'s password is public).

The maintenance bypass key lives only in Render and in your terminal while you smoke-test. It
is never placed in the frontend, never in a URL (query parameters and cookies are ignored) and
never logged.

## 4. Migration rehearsal (on a disposable Neon branch)

`scripts/rehearsal/rehearse.sh` builds the checked-out release and runs it against a disposable
database, then verifies (each item is an automated PASS/FAIL check):

- Flyway: log shows baseline at 1, 3 migrations applied, now at v4; history is exactly
  `1 BASELINE, 2 SQL, 3 SQL, 4 SQL`, all successful; new columns, constraints, indexes and the
  empty `password_reset_tokens` table exist.
- Data: every original `user_id` present; non-seeded users identical in **every original
  column**; seeded accounts keep id, username and `created_at`; all original users default to
  `USER` / `0` / `ACTIVE`; post and comment counts unchanged.
- Maintenance: `/health` open; login, feed and signup → 503 without the key, with a wrong or
  empty key, and with the key in a query parameter or cookie.
- Authentication: demo login (role `USER`, no password field), wrong password and unverified
  account rejected, tampered/missing token → 401, the feed exposes no emails or hashes.
- Demo restrictions: list users, profile and password change, self-delete, deleting or
  deactivating others, admin cleanup → refused; reset request creates no token.
- Signup with `userId=1, role=ADMIN, emailVerified=true` creates an unverified `USER` and
  leaves existing users untouched.
- The admin promotion SQL (section 7) on a rehearsal account → exactly one row; that admin can
  list users and run demo cleanup.
- Restart with a **rotated** `JWT_SECRET`: "No migration necessary", history rows and
  `installed_on` unchanged, old tokens → 401, fresh login works, users still unchanged.
- No email delivered: outbound HTTP(S) is routed to a closed local port **and** the Resend key
  is invalid; the log must show the send failing. Application logs contain none of the run's
  keys, passwords, secrets or tokens.

**Safety guards:** the script refuses to run if the target host equals `PROD_PGHOST`
(including its `-pooler` form), if the target is a pooled endpoint, or if
`flyway_schema_history` already exists. All secrets are generated per run.

**Procedure** (Neon steps are manual; nothing here touches production):

1. Neon → Branches → the backup branch → **Create child branch** `rehearsal-YYYYMMDD`, with
   its own compute.
2. On the rehearsal branch only: Roles → `neondb_owner` → **Reset password** (Neon stores a
   password per role per branch, so production's password is unaffected and the rehearsal
   credentials are isolated). Copy the branch's **direct** connection details.
3. Create an env file **outside the repository** (template in the script header) with the
   rehearsal host, user and new password, plus `PROD_PGHOST` (production's host, for the
   guard) and `EXPECTED_USERS=5`.
4. On the PR branch: `bash scripts/rehearsal/rehearse.sh <env-file>`. Expected:
   `RESULT: 64 passed, 0 failed`.
5. Keep the output; delete the env file. Delete the rehearsal branch after review **[approval]**.

Dry run against a local PostgreSQL 16 fixture shaped like production (V1 schema, the four
seeded accounts plus one ordinary account, no posts): **64 passed, 0 failed**; the guards
refused the production host, a pooler host and an already-migrated database.

## 5. Backup verification and restore

**Backup:** the child branch of production created before deployment (done 2026-10-23).

**Verify it (read-only, manual)** — run on production and on the backup branch; the results
must be identical:

```sql
SELECT 'users' AS t, count(*), md5(string_agg(u::text, '|' ORDER BY user_id)) FROM users u
UNION ALL SELECT 'posts', count(*), md5(coalesce(string_agg(p::text, '|' ORDER BY id), '')) FROM posts p
UNION ALL SELECT 'comments', count(*), md5(coalesce(string_agg(c::text, '|' ORDER BY id), '')) FROM comments c
UNION ALL SELECT 'flyway_history_absent', (to_regclass('public.flyway_schema_history') IS NULL)::int, NULL;
```

Equal counts and fingerprints prove the backup holds exactly production's data, and
`flyway_history_absent = 1` proves it predates the migration. Re-run on production just
before step C1 of the checklist: if production changed after the backup was taken (it
shouldn't: the old service is suspended), take a new backup.

**Restore rehearsal:** the migration rehearsal (section 4) runs on a child of the backup, so it
also proves the restore path "new branch from the backup → point the app at it → it boots,
migrates and serves". Optionally, rehearse Neon's console restore too: create a disposable
child of production `restore-drill`, use Neon's branch restore on **that** branch (from the
backup branch, or a point in time), run the fingerprint query on it and compare with the
backup, then delete it **[approval]**. Never use restore on the production branch in a drill.

**Restore, for real (only if data is damaged)** **[approval]**:
1. `MAINTENANCE_MODE=true` (or suspend the new service).
2. Either (a) create a branch from the backup and set `DATABASE_URL` (and password) on the
   new service to its **direct** endpoint — the rehearsed path; on first boot the release
   migrates it — or (b) restore the production branch from the backup / to the pre-deploy
   timestamp in the Neon console (within the plan's history window; Neon keeps the replaced
   state as a separate branch).
3. Fingerprint check, then the private smoke tests, then reopen.

Data written after the backup is lost; under this plan that is only smoke-test data.
**Retention:** the backup contains personal data; delete it once the release is verified
(suggested within 14 days).

## 6. Before the window: session check (read-only)

Immediately before creating the new service, confirm nothing else holds a session on the
database (an open SQL editor transaction would block V2's `ALTER TABLE`):

```sql
SELECT pid, usename, application_name, state, xact_start, wait_event_type
FROM pg_stat_activity
WHERE datname = current_database() AND pid <> pg_backend_pid();
```

Expected: no rows in state `idle in transaction` or `active`. Close the SQL editor afterwards.

## 7. First administrator

No API can grant `ADMIN` (signup ignores `role`/`userId`; rehearsed). The role is read from
the database on every request.

1. With the bypass key, log in as the owner account (`POST /api/user/login`) and change its
   password (`POST /api/user/update` with `password` and `currentPassword`) before promoting it. Put the JSON bodies in a file outside the repository, send them with
   `--data @file`, then delete the file. Older sessions are signed out.
2. **[approval]** In the Neon SQL editor (production), look up the account, then:
   ```sql
   UPDATE users SET role = 'ADMIN'
   WHERE user_id = <id> AND user_name = '<username>' AND role = 'USER'
     AND status = 'ACTIVE' AND email_verified = true;   -- expect UPDATE 1
   ```
   Never `demo`, `ada`, `alan` or `grace` (section 3).
3. Log in again: the API applies the role immediately; the UI shows the Admin link after a
   fresh login.

## 8. Client-IP verification

Render passes traffic through its proxy (and Cloudflare); `X-Forwarded-For` is appended to,
not replaced, so the app never trusts it. Determine which single-value header Render sets
reliably:

1. Find your public IP: `curl -s https://api.ipify.org`.
2. Send a request that tries to spoof every candidate header:
   ```bash
   curl -s -o /dev/null -H "X-Maintenance-Key: $KEY" \
     -H "X-Forwarded-For: 1.1.1.1" -H "CF-Connecting-IP: 2.2.2.2" \
     -H "True-Client-IP: 3.3.3.3" -H "X-Real-IP: 4.4.4.4" \
     https://<new-render-host>/api/user/get
   ```
3. In the Render log, find the `client-ip diagnostics:` line for that request.
   - `remoteAddr` is the proxy peer: confirm it falls inside `CLIENT_IP_TRUSTED_PROXIES`, or
     set that variable to the observed range.
   - A usable header shows **your real IP**, not the spoofed value, as its **only** value.
4. If one does: `CLIENT_IP_MODE=TRUSTED_HEADER`, `CLIENT_IP_HEADER=<that header>`. If none
   does, keep `UNKNOWN`. Then login, verification and reset submission get no IP-based limit
   (per-account limits and signed or 256-bit tokens protect them); only the endpoints that send
   email fall back to a shared cap (signup 50/h, reset requests 100/h). Per-account and per-user
   limits always apply.
5. Turn diagnostics off at opening.

Counters live in memory: they reset on restart and are not shared across instances. A shared
store would be needed for stronger guarantees.

## 9. Recovery (never by redeploying a pre-release build)

| Situation | Action |
|---|---|
| Migration fails or hangs during the first boot | The service never starts, so nothing is exposed. The database may be at V1, V2 or V3 (section 2) — check `flyway_schema_history` (read-only). Fix the cause; fix-forward PR with green CI if a script changes; redeploy **the new service**. Restore only if data is damaged |
| Release misbehaves after opening | `MAINTENANCE_MODE=true` (save and deploy; confirm the deploy shows the same commit) or suspend the **new** service; diagnose; fix forward through a PR with green CI |
| A bad *new* build | Render → new service → Deploys → redeploy an earlier deploy **of the new service** whose commit is the release merge or later (check the SHA). Never the old service, never an older commit |
| Data damaged | Maintenance mode, then restore (section 5) **[approval]** |
| Frontend problem (e.g. a CSP block) | **Fix forward** by default. Rolling back to a Vercel deployment from **before** the frontend merge is **not safe**: that build calls the old backend host, uses the old API contract and has no CSP or security headers. Roll back only to an earlier deployment built **after** the merge with the new `VITE_API_URL` (verify its commit and its CSP header), and note that after a Vercel rollback new production deployments may not be promoted automatically until the rollback is undone |
| Anything else uncertain | Maintenance mode first; it is always safe and reversible |

The old Render service: never resume it, never use "Deploy a specific commit" on it; delete it
after the release is verified **[approval]**.

## 10. Hostname wiring checks

After the new service exists (its host is `<new-render-host>`):

1. Frontend PR: `vercel.json` `connect-src` contains `https://<new-render-host>`
   (`grep -o 'connect-src[^;]*' vercel.json`), CI green.

## 11. Credential rotation

**JWT_SECRET** is new on the new service, which invalidates every token signed by the old
deployment. Emailed verification
links stop working (users can request new ones); reset links are database tokens and
unaffected. Rotation is rehearsed (section 4). Store it only in Render and a password manager.

Rotate `DATABASE_PASSWORD` or `RESEND_API_KEY` only on evidence of exposure (this release never
logs them). Use a new `MAINTENANCE_BYPASS_KEY` for every window and delete it afterwards.

## 13. Remaining risks after deployment

| Risk | Severity | Mitigation / next step |
|---|---|---|
| Access token stored in localStorage | **Medium** (accepted, separate) | Any script running on the frontend origin can read it until it expires or the session is revoked. CSP and a 4h lifetime reduce this. Fix: cookie-based sessions (separate proposal) |
| Old Render service still exists (suspended) | **Medium** until deleted | Never resume; delete after verification |
| Shared caps on email-sending endpoints while `CLIENT_IP_MODE=UNKNOWN` | **Low-Medium** | A flood can pause new signups/reset emails for up to an hour; logins unaffected |
| Per-instance, in-memory rate limiting | **Medium** | Global caps + per-account limits; shared store if scaled out |
| No `lock_timeout` for migrations | **Low** | Session check before deploying (section 6); a hang ends in a rolled-back, retryable migration |
| Per-account login limit | **Low** | A known username can be locked out for 15 minutes |
| Demo visitors' content visible until cleanup | **Low** | Rate limits; admin cleanup; optional schedule |
| Text other users wrote that mentions a deleted user | **Low** | Admins remove it on request |
| Likes not tracked per user | **Low** | Per-user like table later |
| Signup reveals whether a username or email is taken | **Low** | Accepted; rate-limited |
| Backend container runs as root | **Low** | Non-root `USER` in the Dockerfile |
| Neon backup branch retains personal data | **Low** | Delete after verification |
